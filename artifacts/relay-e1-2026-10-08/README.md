## Hypotheses, judged by the pre-registered criteria
- **H1 (ros-d10 drop lower than ros-d1 by > 10 pp): supported.** S12: 48.8% vs 1.8% (diff 47.0 pp). S4: 47.4% vs -0.1% (diff 47.5 pp). The criterion is met by a wide margin in both scenes, the run-level bootstrap intervals are far apart (S12 [48.0, 49.7] vs [1.3, 2.4]), and the per-run ranges do not overlap. The only changed variable between d1 and d10 is the history depth, so the depth-1 BEST_EFFORT QoS is the cause of about half of in-range deliveries failing, **in the fast-forward configuration used here (sim time_scale 4)**. Whether the same holds in real time is addressed by the post-hoc E1b follow-up (small n).
  - Bootstrap details: the resampling unit is the run (10,000 resamples, percentile interval, seed 20261010) and the statistic is the traffic-weighted pooled drop, so long uncaptured runs dominate the weight. Because the runs are long and homogeneous the interval is narrow; it covers run-to-run variation, not the measurement-definition issues in deviation 4 (the d10 interval being below zero is that boundary mismatch, not negative loss).
  - Receivers with no status message at all (so excluded from numerator and denominator): S12 d1 15 receiver-runs of 240 (10,798 expected deliveries, about 1.5% of the included expected traffic), S12 d10 27 of 240 (15,956, about 2.5%), S4 d1 3 of 40 (831), S4 d10 2 of 40 (685). They are missing at random as far as I can tell, but that is not verified.
- **H2 (S12 capture rate off <= ros <= oracle-1h <= oracle-mh): descriptive only, no ordering can be claimed.** Point estimates: off 0.25, ros-d1 0.35, oracle-1h 0.30, oracle-mh 0.30, ros-d10 0.45. The point estimates are not monotone for either ros variant (ros exceeds both oracles), and all pairwise Wilson intervals overlap, so every pair is reported as "cannot be distinguished". S4: all cells 0-1 captures of 10, also indistinguishable.
- **H3 (ros-d10 closer to oracle-1h than ros-d1 is; descriptive): the point estimates go the opposite way.** S12 gap |ros-d10 - oracle-1h| = 0.15 vs |ros-d1 - oracle-1h| = 0.05, so the d10 gap is the larger one, i.e. the opposite of the hypothesised direction; the Wilson intervals of both ros cells overlap oracle-1h, so this is also not a detectable difference. S4: both gaps 0.10, tie. H3 is therefore not supported, and not refuted either.

## Cumulative capture over time (exploratory, NOT pre-registered)
`docs/media/relay_e1_cumulative_capture.png`: Kaplan-Meier cumulative capture probability for the five S12 modes, runs without capture right-censored at 30 s, shaded Greenwood 95% bands. This was added after the red-team review because "median capture time of captured runs" conditions on capture and is a different population per cell. No time threshold is tested and no p value is reported.

What the figure shows, descriptively: every curve ends between 0.25 (off) and 0.45 (ros-d10) at 30 s with strongly overlapping bands. In the "off" mode the first capture occurs at 11.6 s, whereas the first capture in each sharing mode occurs at 3.0-4.2 s; with 5 vs 6-9 captures this is a pattern in the plot, not a tested effect, and I make no claim about its size. Sharing the sighting does not demonstrably change how many runs end in capture (the 30 s endpoint).

## What the data do and do not show
- **Drop rate:** fixing the self-inflicted QoS loss reduced the per-receiver in-range drop from about 49% to about 2% (S12), the one clear, pre-registered result.
- **Capture rate: no difference detected at n=20.** ros-d1 vs ros-d10 is 7/20 vs 9/20 with overlapping intervals; no cell pair is distinguishable in S12 or S4. The experiment therefore cannot say whether delivery loss matters for capture. It can rule out only very large effects.
- **Sample size needed (planning calculation, not a post-hoc power of these results).** For a two-sided two-proportion z test at alpha 0.05 and 80% power with equal cells, detecting 0.25 vs 0.45 (the off and ros-d10 point estimates) needs about **89 runs per cell** (98 with Fleiss continuity correction); the ros-d1 vs ros-d10 gap (0.35 vs 0.45) needs about **376 per cell** (396 corrected). Formula: n = (z_{1-a/2}*sqrt(2*pb*(1-pb)) + z_{power}*sqrt(p1(1-p1)+p2(1-p2)))^2 / (p1-p2)^2 with pb = (p1+p2)/2. With 20 runs per cell, the experiment can reliably detect only differences far larger than 0.2.
- **Track-valid (descriptive, not tested):** with the fixed 5 s window the sharing modes are far above "off" in S12 (0.70-0.998 vs 0.275) and S4 (0.27-0.62 vs 0.023), and ros-d1/ros-d10 sit between oracle-1h and oracle-mh in S12 (0.756/0.783 vs 0.701/0.998). Medians of n=20 (S12) or n=10 (S4) runs, no intervals.
- **Why oracle is not better than ros here (inference, untested).** The two are not homogeneous: oracle relays the simulator's ground-truth target position with 0.15 Gaussian jitter and no FOV, occlusion or dropout gating, to every informed agent every tick (`perception.relayed_detection`), while ros relays the sender's actual sensor sighting (subject to the sensor model) through the ROS path with receiver-side gates (timeout, range, pose-time tolerance, newest-stamp-only). A plausible reading is that oracle and ros differ in information quality and timing in ways that do not map to "better/worse", and that capture is limited by pursuit geometry rather than by information once track-valid is already high. The first possibility is also compatible with plain noise: 6/20 vs 9/20 is within sampling variation. Nothing in E1 distinguishes these explanations.
- S4 stays near 0 captures as predicted for a hard scene; reported as-is.

## Boundary note (code fix after E1)
E1 ran on commit `7ad48d8`, where `comms.receivers_in_range` used `<=` but `comm_components` and the hop-limited BFS used `<`. A later commit unified all three to `<=` (matching the controller receiver gate, where only `distance > radio_range` is out of range). The difference only matters for pairs at distance exactly 8.0 (floating point), which has probability about zero for continuous positions; inference: negligible effect on E1. E1 is not re-run.

## Deviations and caveats
### A. Implementation choices not covered by the pre-registration (decided before seeing E1 data)
1. **Run order** was not specified; the 150 runs were executed in a fixed pseudo-random order (`shuffle_seed` 20261008) so machine-load drift is not aligned with any cell.
2. **Validity rule** (fixed before E1, after smoke): invalid = wall-clock timeout (240 s, never hit), launch exit code != 0, or no `EPISODE 1 result=` line. A simulated-time timeout (no capture in 30 s) is a valid not-captured outcome. No Traceback appeared in any launch log.
3. **Per-receiver drop definition** (the spec says only "per-receiver drop"): numerator = each receiver's own cumulative `sightings_received_in_range` from the last status message it emitted (self loopback excluded, counted separately); denominator = per sighting, the set of agents within `radio_range` of the sender at publish time (sim file), restricted to keys that a controller really published and to sightings stamped at least 0.05 s before that receiver's last status stamp.
4. **Smoke runs** (S12 ros-d1/ros-d10 seed 101, S4 off/oracle-1h seed 101) were run beforehand in a scratch directory and are not part of E1.
5. **Time scale:** E1 ran headless with the simulator default fast-forward `time_scale` 4.0, with controllers on sim time. The pre-registration did not specify it; this is why real-time behaviour is untested in E1 (see E1b).
6. **Track-valid** uses the status messages the collector received (reliable topic, so the collector can still miss some) and `belief_valid` over cycles with a fresh own pose.

### B. Actual deviations / limitations found afterwards
1. **Runner path bug, data moved afterwards.** The runner was started with a relative `--out`; the launch runs with cwd `ros2_ws`, so the per-run relay accounting files were written to `ros2_ws/artifacts/relay-e1-2026-10-08/runs/<id>/relay/` instead of the run directories. After the 150 runs I copied them unchanged into the matching run directories (1460 files, then deleted the stray tree) and fixed the runner to resolve `--out` to an absolute path in a later commit. Consequently 149 of 150 runs have `working_tree_dirty: true` solely because of the untracked stray directory; no source file was modified.
2. **Drop-rate measurement error near the range boundary.** The receiver classifies in-range with its own cached pose at receive time against the sender position in the message, whereas the sim uses true positions at publish time, so the two can disagree near 8 m. Some receivers therefore show received > expected (59 receiver-runs in S12 ros-d10, 32 in S4 ros-d10, 0 in d1), so d10 drop can be slightly negative; treat d10 as "approximately zero, within about +/-1 pp", not as literal negative loss. Receipts with no fresh own pose are counted as `unclassified` (S12 d1 2,059, d10 3,047; S4 27 each; below 0.5% of in-range receipts), not in the numerator, which biases drop slightly upward. The last 0-0.1 s before shutdown may be missing from the status stream, only partly compensated by the 0.05 s margin.
3. **Track-valid denominator (changed in this revision).** The original metric divided by all fresh cycles of the episode, so its denominator grows with episode length and is mechanically tied to capture time: a run that ends early at capture has a short, easy window (the initial acquisition), a long uncaptured run includes every later loss of track. The original values are kept in `summary.json` as `track_valid_full_episode_*` (S12 medians: off 0.524, oracle-mh 1.0, oracle-1h 0.975, ros-d1 0.95, ros-d10 0.945) but the README and figure now use a **fixed window**: the first min(episode length, 5 s) of each run. Chosen over a caveat-only report because it removes the dependence on how long the episode lasts; remaining limitation: runs captured before 5 s still have a shorter window than runs captured later, and the window mostly measures acquisition speed. Descriptive only.
4. **ROS integration test fixture** was changed (process-group teardown) because the existing tests leaked controller processes that polluted later runs; no behaviour under test changed. Controller processes from before this session (domain 223, started 10:46) were left running.
5. **Fast-forward only.** All E1 runs used time_scale 4, so absolute drop rates may not transfer to real time (E1b tests this with 4 runs per cell).
6. Seeds do not make runs reproducible; each run is one sample. Machine load average was 14-24 from unrelated jobs.
7. Not done (out of scope per the pre-registration): E2, delay/loss models, multi-hop relay.

Note (added after the E1/E1b commit date, 2026-10-08): the shipped default of `shared_sighting_qos_depth` was later changed from 1 to 10 because of this result. All E1 and E1b runs set the depth explicitly through the experiment matrix and are unaffected by the changed default.
